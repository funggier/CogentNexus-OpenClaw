# CogentNexus v0.9.2 — development candidate

v0.9.2 is a Host/CLI/provider-layer release candidate built on the accepted v0.9.1 Recovery Core. It is **not tagged or released yet**.

## Scope

The v0.9.1 OpenClaw Bridge payload remains unchanged at package version `0.9.1`. v0.9.2 changes the external Host/control surface around that Bridge rather than rewriting Ticket admission, durable-result ownership, delivery fences, or exactly-once-ish result handling.

## Added

### Provider-neutral local lifecycle

CogentNexus can supervise either:

- Ollama (`127.0.0.1:11434`)
- LM Studio (`127.0.0.1:1234`)

Both may be installed on the same machine. CogentNexus supervises only the durable `selectedProvider`.

```powershell
.\cnx.cmd start --provider ollama
.\cnx.cmd start --provider lmstudio
```

A successful explicit start remembers the provider. Later `start`/`restart` reuse it. There is no silent provider fallback.

### Transactional provider + OpenClaw route switch

Provider switching now has coordinated durable/config/process boundaries:

1. a durable `providerTransition` records the intended provider before lifecycle mutation;
2. a short-lived exact OpenClaw config rollback copy protects the model-route/config transition until verification commits;
3. the target provider is started/verified before any route-bearing Gateway boundary;
4. a Gateway restart is forced when the route changes, so process state—not just the config file—loads the selected route.

CogentNexus v0.9.2 manages only the narrow OpenClaw fields required by the selected provider:

- default local model route;
- LM Studio provider timeout;
- agent timeout;
- LM Studio llama.cpp unsupported tool-schema keywords.

The accepted v0.9.1 Host-control layer remains the sole CogentNexus owner of `diagnostics.stuckSessionAbortMs` while MANAGED. v0.9.2 deliberately does not compete with that accepted recovery fence.

`selectedProvider` is committed only after provider health, Gateway health, model-route verification and route transaction commit all pass. On host/verification failure, the OpenClaw route rolls back but the durable provider transition remains so the next start resumes the intended target.

`disable`, `reset`, and `uninstall` restore the pre-CogentNexus v0.9.2-owned fields. The PASSTHROUGH boundary then forces and verifies a Gateway process reload before destructive cleanup can proceed.

### LM Studio llama.cpp compatibility profile

Live OpenClaw/LM Studio/Qwen3.5 testing proved that the llama.cpp grammar path requires these schema keywords to be stripped for the observed OpenClaw tool schemas:

```json
{
  "unsupportedToolSchemaKeywords": ["pattern", "maxLength"]
}
```

With that compatibility profile and a sufficient request envelope, the following model-facing surfaces completed successfully:

- minimal;
- `cron`;
- `image_generate`;
- `cron + image_generate`;
- full OpenClaw `coding` profile (26 tools in the observed run).

### Evidence-aware long-running local inference

Live runtime logs proved that a healthy LM Studio/llama.cpp request can remain silent to OpenClaw for more than the default 360-second native stuck-session boundary while prompt prefill is still progressing.

v0.9.2 therefore introduces `cold_model_long_running` for the first expired LM Studio Direct call when both provider and Gateway remain healthy:

- extend the durable model-call deadline once by 600 seconds;
- leave the call active;
- consume no recovery attempt;
- do not restart the provider;
- write durable classification evidence.

A later expiry may enter the accepted v0.9.1 Direct recovery path if all durable result/side-effect fences and provider-recovery gates permit it.

### Bounded provider recovery circuit

Automatic provider recovery is durable and bounded rather than an unbounded restart loop.

Current candidate policy:

| Provider | Max automatic recoveries / rolling hour | Minimum cooldown between attempts | Long-running grace |
| --- | ---: | ---: | ---: |
| Ollama | 3 | 300 s | 0 |
| LM Studio | 2 | 900 s | 600 s |

Every automatic recovery starts its cooldown immediately; the rolling-hour limit is independent. For LM Studio, automatic recoveries are therefore at least 15 minutes apart and never exceed two in a rolling hour.

When either gate blocks recovery, CogentNexus reports `provider_recovery_circuit_open` and does not claim another Direct call for restart recovery. A successful explicit/manual verified provider transition clears that provider's automatic-recovery budget.

### LM Studio request timeout envelope

The verified v0.9.2-owned request profile is:

```text
models.providers.lmstudio_local.timeoutSeconds = 1100 s
agents.defaults.timeoutSeconds                 = 1200 s
```

The provider request expires before the enclosing agent timeout. Separately, the accepted v0.9.1 MANAGED watchdog compatibility moves OpenClaw's native stuck-session abort to approximately 24 hours so it remains outside the normal CogentNexus recovery horizon. That watchdog field is snapshotted/restored by v0.9.1, not by the v0.9.2 route transaction.

### Verified native/PASSTHROUGH Gateway boundary

`disable` no longer treats an on-disk config restore as sufficient proof. After the accepted v0.9.1 PASSTHROUGH transition, v0.9.2 restores its route/request-timeout/schema-compat fields, forces a Gateway restart (or start fallback), and requires a healthy post-boundary status probe.

`reset` and `uninstall` reuse that boundary and fail closed before destructive cleanup if the native Gateway route cannot be reloaded. Reset also forces a second Gateway boundary after installing the fresh MANAGED provider route and before committing the fresh provider selection.

### Aircraft-style pre-flight inspection

Read-only diagnostic namespace:

```powershell
.\cnx.cmd check system
.\cnx.cmd check system --provider lmstudio
.\cnx.cmd check provider
.\cnx.cmd check gateway
.\cnx.cmd check model
.\cnx.cmd check storage
.\cnx.cmd check recovery
.\cnx.cmd check delivery
.\cnx.cmd check resources
```

Full verdicts:

- `READY` (exit 0)
- `READY_WITH_WARNINGS` (exit 1)
- `NOT_READY` (exit 2)
- `INDETERMINATE` (exit 3)

All `check` commands are observational and explicitly report that no state was changed.

### Provider-aware install/reset

Windows installer:

```powershell
.\scripts\install.ps1 -Provider ollama
.\scripts\install.ps1 -Provider lmstudio
```

POSIX installer:

```sh
./scripts/install.sh --provider ollama
./scripts/install.sh --provider lmstudio
```

If exactly one supported provider is installed, the provider option may be omitted. If both are installed on a fresh state, explicit selection is required.

`reset` returns to fresh-install provider semantics. With both providers installed:

```powershell
.\cnx.cmd reset --provider ollama
# or
.\cnx.cmd reset --provider lmstudio
```

The v0.9.1 explicit-`y`, PASSTHROUGH-first, verified reset/uninstall safety boundaries remain in force.

## Recovery compatibility

The accepted v0.9.1 destructive Direct-recovery classifier/order remains unchanged once a call is truly recovery-eligible:

1. quiesce Gateway/provider;
2. reconcile durable result/delivery fences while inference is impossible;
3. authorize at most one eligible Direct recovery;
4. restart selected provider/Gateway;
5. consume durable recovery authority.

v0.9.2 adds evidence-aware guards **before** that sequence so a healthy long-running LM Studio prefill is not mistaken for a dead provider.

Deterministic request-shape failures such as provider HTTP 4xx/schema/grammar rejection are classified as non-retryable provider protocol errors and do not justify a provider restart.

A process exit code or top-level wrapper status is not treated as proof of inference success; inner/durable completion evidence remains authoritative.

## Validation status before release

The repository validation matrix targets Linux, Windows and macOS with Python 3.11/3.14, Python compilation, unit tests, plugin tests/evaluation/audit/validation, installer syntax, baseline consistency and release packaging.

Provider-specific live evidence is now substantially stronger for LM Studio than at the beginning of v0.9.2 development: route/transport, reasoning-off, isolated tool schemas, combined schemas, full coding schema, cold-prefill behavior and timeout layers have all been exercised natively on Windows.

Still required before tag/release:

- repository regression suite/matrix confirmation for the final route/recovery/process-boundary modules;
- final provider lifecycle/reset/disable/uninstall live acceptance on the v0.9.2 candidate;
- final review that v0.9.1 Recovery Core/delivery invariants remain unchanged;
- release artifact/hash generation only after those gates pass.
