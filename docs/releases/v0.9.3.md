## Ownership-safe install and upgrade

Installation over an existing deployment is transactional and fail-closed:

1. inventory current/new/legacy product surfaces before mutation;
2. recover only a valid, marker-authorized incomplete fresh-install transaction;
3. prove plugin/package identity before mutation;
4. move an existing managed deployment to native/PASSTHROUGH before replacing controlled surfaces;
5. stage/validate the new skill and plugin;
6. create and verify exact ownership metadata;
7. enable MANAGED only after installation-owned postconditions pass.

Ambiguous, mixed, corrupted, or foreign layouts are not adopted or deleted automatically.

## Ticket-first durable intent and Direct execution

Eligible owner input is durably admitted as a Ticket before inference while ordinary conversational work can remain in the lightweight DIRECT lane rather than being forced into a heavyweight workflow.

Durable authority is fenced by Ticket/session/generation/runtime state. A transient process observation or transient SQLite BUSY read is not allowed to silently revoke Host ownership and create duplicate inference.

## Single-owner recovery and native restart fencing

For genuinely pre-response interrupted Direct work, Host-authorized Direct Recovery preserves the owner session/generation and original provider/model provenance.

OpenClaw native restart continuation is consumed only when durable evidence proves that the exact continuation belongs to the same CNX-owned recovery. Ordinary user prompts and unproven native behavior are not globally suppressed.

Elapsed time alone is not recovery authority.

## Durable result and delivery boundary

`response_ready` and the durable Direct result are evidence boundaries. Once an exact durable result exists:

- delivery transport may retry that exact result;
- inference must not be regenerated merely because delivery is uncertain;
- completed/cancelled/failed Tickets remain fenced against stale workers;
- possible external side effects require idempotency/receipt/read-after-write evidence before repetition.

CogentNexus-OpenClaw provides an exactly-once-ish durable delivery boundary for its owned delivery path, not a universal exactly-once guarantee for arbitrary external systems.

## Direct Dashboard `NO_REPLY` repair

The pre-repair integration could treat any non-empty model final as visible durable content. OpenClaw uses bare `NO_REPLY` as a silent sentinel, so CogentNexus marker decoration could accidentally transform that sentinel into a visible non-sentinel payload.

Task 191 repairs this boundary:

- bare `NO_REPLY` / `no_reply` is never staged as a durable visible Dashboard result;
- for a genuine direct Dashboard Ticket whose natural final is exactly the bare sentinel, CogentNexus may request at most one same-run OpenClaw `before_agent_finalize` revision;
- CogentNexus does not fabricate the answer text;
- this case does not create an external Direct Recovery run or duplicate Ticket/model-call path.

Repository validation on exact repaired candidate `050ab53f...` passed the full Validate matrix, PS5.1 Acceptance Smoke, Windows Installer Pack Smoke, and the focused Task-191 regressions.

## Reset and uninstall

There is intentionally no `cnxclaw install` command. Installation is performed from the source/release archive installer.

Destructive lifecycle commands require explicit `y` confirmation:

```powershell
.\cnxclaw.cmd reset
.\cnxclaw.cmd uninstall
```

`reset` clears/reconstructs only CogentNexus-OpenClaw-owned state to a fresh-install state.

`uninstall` returns to native/PASSTHROUGH and removes only CogentNexus-OpenClaw-owned surfaces. External OpenClaw, Ollama runtimes/models/data, unrelated workspace data, and unrelated/future CogentNexus namespaces are preserved.
