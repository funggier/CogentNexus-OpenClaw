# CNX-20260919-428 — OpenClaw 9.5 Supervisor Cold-Start Grace Repair

Status: `COMPLETE`

Parent: `CNX-20260919-427`

## Trigger

During CNX-427 post-upgrade qualification on live OpenClaw `2026.9.5`, the CogentNexus external supervisor repeatedly classified a valid cold-starting Gateway as hard-unresponsive and issued:

`lifecycle restart --reason "CogentNexus-OpenClaw external supervisor confirmed an unresponsive Gateway"`

This created a self-inflicted restart loop and could prevent the OpenClaw 9.5 runtime from ever reaching its admitted ready state.

## Root cause

The v0.9.5 Host façade inherited the legacy hard-hang rule:

1. run `gateway_fast_probe()`;
2. sleep `HARD_HANG_CONFIRM_DELAY_SECONDS = 1.0`;
3. run the fast probe again;
4. if both fail, perform hard-hang recovery.

That rule assumes a healthy Gateway becomes responsive within roughly one second.

Live OpenClaw 2026.9.5 disproved that assumption on this host:

- cold boot began around `19:43:31 +07`;
- HTTP listener became available around `19:44:13.586 +07` (~42.4 s);
- `sidecars.model-runtime` produced an event-loop stall of roughly 38 s;
- `gateway ready` was emitted at `19:45:01.621 +07`;
- total cold-start time was about 90.7 s.

Therefore two failed probes one second apart are not sufficient evidence of a hard hang while OpenClaw has an active boot lifecycle.

## Required semantics

1. The supervisor MUST NOT restart a Gateway merely because fast probes fail during a bounded, authoritative OpenClaw boot/restart interval.
2. Startup grace MUST be grounded in OpenClaw runtime state, not an unbounded sleep or blind fixed delay.
3. The grace MUST be bounded so a genuinely hung Gateway eventually returns to the existing hard-hang recovery path.
4. Healthy idle behavior, durable wake authority, direct recovery, provider ownership, and maintenance convergence MUST remain unchanged.
5. The repair MUST remain provider-neutral.
6. No OpenClaw dist patch is part of the production fix.

## Repair contract

Use OpenClaw's shared-state database:

`~/.openclaw/state/openclaw.sqlite`

and table:

`gateway_boot_lifecycle`

to inspect the newest incomplete Gateway boot.

While its age is at most `180s`, a double fast-probe failure is classified as:

- result: `gateway-starting`;
- action: `none`;
- wakeReason: `gateway/startup-grace`;
- heavyPath: `false`.

After the bounded grace expires, preserve the existing hard-hang restart behavior.

## TDD requirements

Focused tests MUST prove:

- an active boot inside the grace suppresses restart;
- the authoritative SQLite boot row is read correctly;
- the grace expires after the bounded interval;
- an expired/absent grace still allows the existing confirmed hard-hang recovery;
- transient failure and healthy idle paths retain prior behavior.

## Live qualification

Live acceptance MUST prove:

1. installed source equals the reviewed source byte-for-byte;
2. an actual OpenClaw 9.5 boot row inside the grace is classified `gateway-starting`;
3. a sentinel replacement of `_restart_unresponsive_gateway` is not invoked during that boot;
4. OpenClaw reaches `gateway ready`;
5. a stale `healthy-runtime` maintenance marker converges through the supported lifecycle path;
6. recurring `CogentNexus-OpenClaw-Supervisor` returns `LastTaskResult=0`;
7. no new `gateway.restart.request` is emitted by the repaired supervisor;
8. Gateway/Discord health remains GREEN.
