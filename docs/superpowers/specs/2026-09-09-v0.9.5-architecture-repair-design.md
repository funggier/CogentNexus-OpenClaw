# CogentNexus-OpenClaw v0.9.5 Architecture Repair Design

Date: 2026-09-09
Status: Approved design pending written-spec review
Base release: v0.9.4
Base commit: `40352b3c8b6b9c98c1dfdead5d197f976976bc9f`
Target release: v0.9.5
Working branch: `agent/v0.9.5-architecture-repair`

## 1. Purpose

v0.9.5 is an architectural repair release. It is not a broad feature release and it is not a rollback to v0.9.3.

The release exists because v0.9.4 improved several local safety boundaries while also coupling provider ownership, Host mode, plugin capability, delivery settlement, Supervisor behavior, and configuration mutation too tightly. The result is a system that can be safer at individual boundaries while becoming less capable, less deterministic, and harder to reason about as a whole.

The v0.9.5 objective is to restore the behavioral simplicity expected from v0.9.3 while retaining the proven safety fixes introduced after it.

The governing product invariant is:

> CogentNexus capability is independent of the inference provider selected by OpenClaw.

A user must be able to use the normal OpenClaw web chat provider/model selector without leaving CogentNexus, changing CogentNexus mode, restarting the Gateway, or losing Ticket, workflow, context, recovery, or delivery semantics.

## 2. Design compass

This design follows the CogentNexus semantic invariant:

- **Cogent**: preserve coherence, meaning, direction, and identity across retries, provider changes, restarts, recovery, and delivery.
- **Nexus**: connect OpenClaw, providers, sessions, Tickets, workflows, recovery, and transports without allowing one layer to redefine another layer's authority.

The architecture must preserve the user's intent while allowing the inference implementation beneath it to change dynamically.

## 3. Primary goals

v0.9.5 MUST:

1. Allow provider/model switching through normal OpenClaw UI behavior while CogentNexus remains active.
2. Keep Direct and Durable capabilities available across all providers supported by OpenClaw.
3. Make Ticket/workflow/context/recovery/delivery logic provider-neutral.
4. Retain safe provider-specific local lifecycle adapters where justified, especially Ollama.
5. Replace delivery correlation heuristics with a canonical identity chain.
6. Use one delivery state machine across Web Chat, Discord, and future surfaces.
7. Preserve exact session-generation ownership and reject stale or ambiguous settlement evidence.
8. Reduce healthy-path configuration mutation and Supervisor write authority.
9. Introduce a cross-subsystem behavior matrix as a release gate.
10. Migrate v0.9.4 Cloud-pass-through installations without changing the user's OpenClaw provider/model/auth route.
11. Restore current coordination documents so repository coordination state matches the actual public release state.

## 4. Non-goals

v0.9.5 MUST NOT:

- create a new provider framework that replaces OpenClaw routing;
- store or manage Cloud provider credentials;
- implement vendor-specific Cloud auth or model discovery;
- treat provider switching as a Host mode transition;
- infer the current provider from credentials or model-name heuristics when it is not necessary;
- redesign the Ticket Store, Knowledge Store, evaluation layer, or admission classifier unless required by these boundaries;
- remove proven safety fixes merely to match old source code;
- force-push or rewrite public release history;
- publish v0.9.5 before migration, behavior-matrix, CI, Windows lifecycle, and live Web Chat acceptance all pass.

## 5. Behavioral reference strategy

v0.9.3 is the behavioral reference, not the source-code target.

The implementation should restore these behavioral properties:

- provider selection does not silently remove Ticket capability;
- simple Direct requests remain simple;
- Durable requests never dead-end solely because the selected provider is Cloud or unknown to CogentNexus;
- restart/recovery does not create unrelated lifecycle mutations;
- delivered responses converge without guessing identity;
- disabled CogentNexus returns to truly native OpenClaw behavior.

v0.9.4 safety fixes remain valid unless a replacement design provides equal or stronger guarantees.

## 6. KEEP / REWORK / REMOVE / RESTORE classification

### 6.1 KEEP

Keep these concepts and proven fixes:

- Ticket-first continuity and durable Ticket state;
- terminal Ticket fences;
- owner session and owner generation fences;
- exact receipt safety: ambiguous Discord receipts must not complete a Ticket;
- durable assistant-delivery staging;
- delivery-before-inference recovery fences;
- event-authorized provider recovery rather than timer-only destructive recovery;
- quiescence owner/token fencing, bounded locking, TTL, and stale reclaim;
- optimistic/fail-closed config mutation behavior;
- stale pending-delivery wake filtering;
- native OpenClaw behavior when CogentNexus is disabled;
- exact-SHA and checksum release provenance.

### 6.2 REWORK

Rework:

- Host state model;
- provider ownership semantics;
- plugin providerMode gating;
- lifecycle start/stop semantics that currently imply a global selected provider;
- Direct/Durable delivery correlation;
- Web Chat and Discord delivery specialization;
- session lifecycle identity;
- Supervisor write authority;
- migration semantics from v0.9.4;
- release testing topology.

### 6.3 REMOVE

Remove from active-runtime semantics:

- Cloud provider == Host passthrough mode;
- provider choice changing CogentNexus capability;
- `cnxclaw cloud` as a required provider-selection transition;
- automatic Gateway restart solely because the user changed provider/model;
- routine AGENTS.md mutation due to provider changes;
- global desiredProvider state as authority for CogentNexus capability;
- "latest run in session" settlement guesses;
- time/quiet-period as a substitute for exact delivery identity when exact evidence is required.

Compatibility aliases may remain temporarily if needed for migration or operator clarity, but they must not preserve the old architectural coupling.

### 6.4 RESTORE BEHAVIOR

Restore the behavior that CogentNexus stays present while OpenClaw performs its normal routing.

Changing provider/model is an inference-route change, not a CogentNexus lifecycle transition.

## 7. Provider and capability boundary

### 7.1 Authority split

OpenClaw owns:

- provider selection;
- model selection;
- Cloud authentication;
- routing;
- vendor-specific request construction;
- vendor-specific Cloud lifecycle and availability semantics.

CogentNexus owns while active:

- Ticket admission and identity;
- Direct/Durable lane semantics;
- workflow state;
- context continuity;
- recovery orchestration;
- inference-attempt bookkeeping;
- delivery staging and confirmation;
- idempotency;
- session ownership fences.

### 7.2 Core invariant

`provider selection MUST NOT determine CogentNexus capability`.

Changing provider or model MUST cause:

- zero CogentNexus mode changes;
- zero Host-generation increments;
- zero mandatory Gateway restarts;
- zero policy mutations;
- zero plugin enable/disable transitions;
- zero Ticket replacement;
- zero workflow replacement.

### 7.3 Unknown/future providers

A provider unknown to CogentNexus but supported by OpenClaw MUST still support CogentNexus Direct and Durable operation.

CogentNexus may lack provider-specific process-management capability for that provider, but it MUST NOT lack Ticket/workflow/context/delivery capability.

## 8. Runtime state model

### 8.1 v0.9.4 problem

The v0.9.4 state model mixes CogentNexus authority with provider lifecycle concepts through values such as:

- `mode = managed | passthrough | maintenance`
- `desiredProvider = running | stopped | unchanged`
- plugin `providerMode = managed | passthrough`

This makes a provider route choice capable of changing CogentNexus behavior.

### 8.2 v0.9.5 state

The target conceptual state is:

```text
cnxMode = active | disabled | maintenance
desiredGateway = running | stopped
providerOwnership = openclaw
managedLocalAdapters = {
  ollama: auto | disabled
}
```

The exact persisted schema may use compatibility fields during migration, but external semantics MUST match this model.

### 8.3 Meaning

- `active`: CogentNexus interception, Ticket, workflow, recovery, context, and delivery are enabled.
- `disabled`: CogentNexus does not intercept new turns; OpenClaw behaves natively.
- `maintenance`: CogentNexus intentionally suppresses normal inference-capable operation for an explicit maintenance transition.

No state value represents "Cloud provider mode".

## 9. Local provider adapters

Local provider lifecycle support is optional capability, not global authority.

Ollama may retain a managed adapter for:

- health probing;
- process start;
- process recovery;
- process stop when explicitly operator-owned.

The adapter may act only when evidence shows that the affected inference attempt used Ollama and the recovery policy authorizes process action.

If the active OpenClaw route is Cloud and Ollama is stopped, the Supervisor MUST NOT wake Ollama merely because a global desiredProvider value says "running".

Provider-specific process recovery MUST never enable or disable Ticket capability.

## 10. Inference-attempt identity

Provider/model belong to an inference attempt, not to a Ticket or Session identity.

Canonical relationship:

```text
TicketID             stable intent/work identity
SessionID            stable logical conversation identity
SessionGeneration    physical OpenClaw session incarnation
InferenceAttemptID   one inference attempt
RunID                OpenClaw run correlated to that attempt
DeliveryAttemptID    one final-payload delivery attempt
```

An inference attempt records at least:

```text
attemptId
ticketId
sessionId
sessionGeneration
runId
provider
model
startedAt
endedAt
outcome
```

Provider/model are metadata. They do not participate in Ticket or Session identity.

Example:

```text
Ticket A
  Attempt 1 -> Ollama/model-A -> connection refused
  Attempt 2 -> OpenAI/model-B -> success
  Delivery 1 -> confirmed
  Ticket A -> completed
```

Ticket A and its logical Session remain unchanged.

## 11. Recovery ownership

Recovery is divided into three layers.

### 11.1 CogentNexus recovery

Provider-neutral and authoritative for:

- interrupted Tickets;
- workflow continuation;
- inference attempt retry eligibility;
- attempt limits;
- context continuation;
- durable result ownership;
- delivery retry;
- terminal state convergence.

### 11.2 OpenClaw/provider recovery

Default owner of:

- Cloud auth failures;
- vendor routing/model resolution;
- vendor rate limits;
- Cloud endpoint lifecycle;
- provider-specific request errors.

CogentNexus consumes attempt outcomes and determines workflow consequences without pretending to control the external Cloud service.

### 11.3 Managed-local recovery

For explicitly supported local adapters, CogentNexus may recover the local process only with explicit attempt/provider evidence and authorized recovery classification.

Elapsed time alone is not destructive recovery authority.

## 12. Canonical delivery model

### 12.1 Problem

v0.9.4 delivery spans multiple hooks and fallback paths, including `reply_dispatch`, `reply_payload_sending`, `message_sent`, `cnx_assistant_delivery`, session-generation fences, quiet periods, and recovery paths. Several individual safety fixes are valid, but ownership is fragmented.

### 12.2 State machine

All surfaces use one canonical state machine:

```text
response_ready
  -> delivery_prepared
  -> delivery_staged
  -> transport_accepted
  -> delivery_confirmed
  -> ticket_completed
```

### 12.3 DeliveryAttempt

Each delivery attempt has one authoritative identity:

```text
deliveryAttemptId
ticketId
inferenceAttemptId
runId
ownerSessionKey
ownerGeneration
surface
payloadHash
idempotencyKey
state
evidenceType
createdAt
updatedAt
```

The durable database is the authority for state transition.

### 12.4 Required rules

- Never select "latest run in session" to guess settlement ownership.
- A receipt without sufficient exact identity cannot complete a Ticket.
- Duplicate callbacks are idempotent no-ops.
- A callback from an obsolete session generation cannot settle a current delivery attempt.
- The same Ticket/final payload/owner generation produces a stable idempotency authority.
- A durable final payload suppresses unnecessary inference regeneration.
- Delivery recovery retries delivery before considering new inference.

## 13. Surface adapters

Web Chat, Discord, and future surfaces use one Delivery Core.

```text
Canonical Delivery Core
  +-- Web Chat adapter
  +-- Discord adapter
  +-- future adapter
```

Surface adapters translate OpenClaw hooks into canonical evidence. They do not define Ticket completion policy.

Examples:

```text
Web Chat:
  exact session append / supported post-persistence evidence
    -> confirm(DeliveryAttemptID, SESSION_APPEND)

Discord:
  exact run + session transport receipt
    -> confirm(DeliveryAttemptID, TRANSPORT_ACCEPTED)
```

If a surface cannot provide enough identity:

- do not complete;
- do not guess;
- do not immediately regenerate inference;
- retain the durable DeliveryAttempt and let recovery reconcile it.

## 14. Session lifecycle

Separate logical CogentNexus Session identity from the physical OpenClaw session incarnation.

Session generation changes only when ownership materially changes, such as delete/replace/rotation to a new authoritative OpenClaw session.

The following MUST NOT increment session generation by themselves:

- provider change;
- model change;
- ordinary context compaction;
- Gateway restart when the same session remains authoritative.

Stale evidence from an old generation must fail closed.

## 15. Supervisor and single-writer authority

### 15.1 Configuration authority

The bounded CogentNexus administrative writer owns:

- plugin installation/configuration;
- enable/disable;
- policy installation/removal;
- migrations;
- reset/uninstall-owned mutations.

OpenClaw owns provider/model/auth route state.

### 15.2 Supervisor role

The Supervisor owns:

- observation;
- Ticket/recovery reconciliation;
- safe recovery actions;
- liveness checks relevant to active CogentNexus work.

The Supervisor MUST NOT on the healthy path:

- rewrite OpenClaw provider/model configuration;
- change CogentNexus mode because the provider changed;
- perform routine plugin configuration writes;
- restart a local provider unrelated to the affected inference attempt.

### 15.3 Quiescence lease

Keep the existing owner/token/TTL/stale-reclaim quiescence mechanism for bounded administrative transactions.

Use it around install/upgrade/enable/disable/reset or other explicit mutation transactions where Supervisor reconciliation could conflict.

Do not use quiescence as a permanent dependency for normal provider switching or healthy inference.

### 15.4 External config races

If OpenClaw configuration changes concurrently with a CogentNexus administrative transaction:

- fail closed;
- preserve user state;
- reread current configuration;
- never overwrite an unrecognized external change blindly.

## 16. v0.9.4 to v0.9.5 migration

Migration MUST be deterministic and provider-neutral.

Required mappings:

```text
v0.9.4 managed
  -> v0.9.5 active

v0.9.4 maintenance
  -> v0.9.5 maintenance

v0.9.4 passthrough + plugin disabled
  -> v0.9.5 disabled

v0.9.4 passthrough + plugin enabled
  -> v0.9.5 active
```

The final mapping is the v0.9.4 `cnxclaw cloud` case and is release-critical.

Migration MUST preserve:

- OpenClaw provider selection;
- model selection;
- credentials/auth configuration;
- current OpenClaw route;
- Ticket database;
- active/nonterminal Ticket ownership;
- durable delivery state;
- user AGENTS.md content outside the CogentNexus-owned block.

Migration MUST NOT attempt to infer provider identity from credentials or model strings unless a narrowly justified compatibility operation explicitly requires it.

## 17. `cnxclaw cloud` disposition

v0.9.5 no longer requires a Cloud transition to obtain Cloud inference while CogentNexus is active.

Preferred behavior:

- normal provider switching occurs in OpenClaw;
- CogentNexus remains active;
- `cnxclaw cloud` is removed from primary guidance.

For compatibility, the command may temporarily remain as a deprecated no-provider-mutation compatibility operation if removing it would create avoidable upgrade breakage. It MUST NOT set a reduced-capability plugin mode.

The implementation plan must choose delete-vs-deprecate based on testable compatibility impact, while preserving the invariant above.

## 18. Coordination-state repair

At the start of the v0.9.5 implementation line, repository coordination authority must be updated so `ACTIVE.md` and `STATUS.md` no longer claim the repository is blocked before v0.9.4 migration when v0.9.4 is already published.

Coordination documents must identify:

- v0.9.4 as the current public baseline;
- `agent/v0.9.5-architecture-repair` as the active v0.9.5 line;
- the approved v0.9.5 architecture-repair objective;
- the next concrete implementation task.

## 19. Testing strategy

### 19.1 TDD requirement

Production repairs use:

1. RED test demonstrating the violated contract;
2. minimal boundary repair;
3. GREEN focused tests;
4. relevant integration matrix;
5. full suite.

### 19.2 Behavior matrix

The release needs a central cross-subsystem matrix covering representative combinations of:

```text
Provider:
  local managed-capable
  Cloud/native
  unknown/future

Request:
  Direct
  Durable

Surface:
  Web Chat
  Discord

Runtime:
  normal
  Gateway restart
  session replacement
  compaction

Delivery:
  exact receipt
  duplicate receipt
  missing receipt
  stale receipt

Recovery:
  provider failure
  interrupted run
  delivery failure
```

The suite should use invariant coverage and pairwise/cross-boundary cases rather than an uncontrolled full Cartesian product.

### 19.3 Release-blocking scenarios

At minimum:

1. Ollama -> Cloud provider in the same session: Ticket and generation unchanged.
2. Cloud provider A -> Cloud provider B during Durable workflow: workflow continues.
3. Unknown OpenClaw-supported provider: Direct and Durable remain available without a CogentNexus provider adapter.
4. Discord concurrent runs: ambiguous receipt settles none; exact receipt settles exactly one.
5. Web Chat stale-generation evidence cannot settle the new generation.
6. Gateway restart preserves nonterminal Ticket ownership.
7. Provider failure does not imply Ticket loss.
8. Durable final payload plus delivery failure does not trigger unnecessary inference regeneration.
9. Provider switch causes no CNX config writes, mode changes, policy mutations, or mandatory Gateway restart.
10. Disabled CogentNexus remains native OpenClaw.
11. v0.9.4 Cloud-pass-through upgrade becomes active v0.9.5 without route/auth/model mutation.

## 20. Release gates

v0.9.5 MUST NOT publish until all gates pass for one exact candidate SHA.

### Gate 1: source/unit/schema/migration

- TypeScript build and focused tests;
- Python focused tests;
- database migration tests;
- state migration tests;
- metadata consistency.

### Gate 2: provider-independent behavior matrix

All release-blocking invariants pass.

### Gate 3: full repository suites

- plugin validation;
- full Vitest suite;
- full Python suite;
- baseline/packaging/provenance checks;
- GitHub CI green for exact candidate.

### Gate 4: Windows lifecycle acceptance

For exact candidate:

- install-over from supported v0.9.4;
- restart;
- disable -> native OpenClaw parity;
- enable;
- reset/uninstall behavior if touched by migration changes;
- installed bytes/provenance verified.

### Gate 5: live provider-switch acceptance

Using the normal OpenClaw Web Chat provider selector, exercise at least:

```text
Ollama -> Cloud A -> Cloud B -> Ollama
```

while CogentNexus stays active.

Prove:

- CogentNexus capability remains active;
- Ticket identity is preserved;
- relevant logical Session identity is preserved;
- no unintended Host generation change;
- no unintended Gateway restart;
- no provider-triggered policy mutation;
- no lost durable work;
- no lost final delivery.

## 21. Error handling principles

- Fail closed on ambiguous identity.
- Preserve user-owned OpenClaw configuration on migration or concurrency conflict.
- Prefer durable waiting/reconciliation over speculative repeated inference.
- Keep terminal intent authoritative.
- Never convert a transport-visible response into completion without supported durable evidence.
- Never treat provider change as failure or recovery by itself.
- Never use a healthy-path timer alone to authorize destructive provider recovery.

## 22. Implementation boundaries

The implementation plan should decompose work into independently testable phases rather than one broad rewrite.

Recommended phase boundaries:

1. coordination-state correction and v0.9.5 contract tests;
2. provider/capability decoupling;
3. Host state migration and local-adapter isolation;
4. canonical inference-attempt identity;
5. canonical delivery core and surface adapters;
6. session-generation lifecycle repair;
7. Supervisor/single-writer cleanup;
8. behavior matrix;
9. metadata/version migration to 0.9.5;
10. exact-candidate CI and Windows/live acceptance;
11. release provenance and publication.

Each phase must preserve a runnable repository and must not silently weaken existing safety fences.

## 23. Architectural success criteria

v0.9.5 is architecturally successful when the following statement is true:

> CogentNexus-OpenClaw behaves as a durable orchestration and continuity layer above OpenClaw inference routing. OpenClaw may change providers and models freely, while CogentNexus preserves the same intent, Ticket, workflow, context, recovery, session ownership, and delivery guarantees without requiring provider-specific CogentNexus mode transitions.

The strongest practical test is simple:

> A user can select a different provider in the normal OpenClaw web chat and continue working as though only the intelligence backend changed, not the CogentNexus system around it.

## 24. Deferred questions for implementation planning

These are implementation decisions, not unresolved product requirements:

1. whether `cnxclaw cloud` is removed immediately or retained temporarily as a deprecated compatibility no-op/transition helper;
2. whether the new state is persisted as a schema-version bump or represented through a compatibility translation layer first;
3. whether canonical inference/delivery identities extend existing tables or introduce narrowly scoped new tables;
4. which exact OpenClaw post-persistence hook/evidence should be the strongest Web Chat confirmation source on the validated baseline.

Any choice must satisfy the approved invariants in this document.

## 25. Explicitly rejected approaches

### Patch only the Cloud durable block

Rejected because it would leave Host/provider/capability coupling intact and permit the same class of regression elsewhere.

### Make CogentNexus own all provider routing

Rejected because it duplicates OpenClaw, expands credential/vendor responsibility, and couples CogentNexus development speed to every provider API.

### Roll back wholesale to v0.9.3

Rejected because post-v0.9.3 work contains important safety repairs, including exact delivery ownership, config-race mitigation, stale wake filtering, and recovery fences.

## 26. Final design decision

v0.9.5 will repair architecture rather than continue accumulating isolated compatibility patches.

The release will preserve v0.9.4 safety improvements where they are sound, restore v0.9.3-like behavioral simplicity where it was lost, and establish provider-independent CogentNexus semantics as an explicit release contract.
