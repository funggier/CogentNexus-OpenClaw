# v0.9.5 Provider, Runtime, and Command Repair Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Decouple CogentNexus capability and lifecycle from OpenClaw provider/model routing while introducing the approved `cnxclaw local ollama ...` command surface.

**Architecture:** OpenClaw remains the sole owner of provider/model/auth/route. CogentNexus top-level lifecycle becomes provider-neutral; local Ollama management is an optional adapter namespace. The v0.9.4 `managed/passthrough` provider coupling is migrated into a CNX authority state that distinguishes active/disabled/maintenance without representing Cloud as a mode.

**Tech Stack:** Python 3, TypeScript, OpenClaw plugin hooks/config, SQLite state, unittest/pytest-style repository tests, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-09-v0.9.5-architecture-repair-design.md`; normative amendment `docs/superpowers/specs/2026-09-09-v0.9.5-local-provider-command-contract.md`

## Global Constraints

- Provider/model routing belongs to OpenClaw.
- CogentNexus Direct/Durable/Ticket/workflow/context/recovery/delivery capability must remain available for every OpenClaw-supported provider.
- Provider switching must cause zero CNX mode changes, zero Host-generation increments, zero mandatory Gateway restarts, zero policy mutations, and zero plugin enable/disable transitions.
- `cnxclaw` must not store or manage Cloud credentials.
- Local process lifecycle is optional adapter capability and must not select the OpenClaw route.
- Preserve v0.9.4 exact-delivery and recovery safety fences.
- No force push.
- Production repairs follow RED -> minimal fix -> GREEN.
