# CogentNexus-OpenClaw v0.9.5 Idle Quiescence and Single-Wake Contract

Date: 2026-09-09
Status: Approved normative amendment
Target release: v0.9.5
Working branch: `agent/v0.9.5-architecture-repair`
Parent design: `docs/superpowers/specs/2026-09-09-v0.9.5-architecture-repair-design.md`
Related command amendment: `docs/superpowers/specs/2026-09-09-v0.9.5-local-provider-command-contract.md`

## 1. Purpose

This document makes idle behavior, recovery wake ownership, and user-visible responsiveness release-critical for v0.9.5.

The system must not create recurring UI disturbance, mouse busy-cursor/spinner symptoms, unnecessary CPU/process churn, or overlapping recovery work simply because background checks exist.

The normative idle invariant is:

> No actionable work means no heavy wake.

## 2. Historical defect class

The v0.9.4 line exposed a concrete failure mode where a stale pending assistant-delivery row was not actionable under the delivery contract but still made `durable_work_hint()` return true. That false-positive wake forced the heavy legacy Supervisor path every minute and accumulated repeated attempts.

The defect class is broader than that one row. Any background checker that treats stale, irrelevant, duplicate, provider-unrelated, generation-obsolete, or otherwise non-actionable state as a wake reason can produce repeated process activity and cross-check interference.

v0.9.5 therefore treats wake authorization as an ownership problem, not merely a polling-frequency problem.

## 3. Core invariants

### 3.1 Idle means quiescent

When there is no actionable CogentNexus work:

```text
no heavy Supervisor wake
no provider lifecycle probe that requires process work
no recovery scan beyond bounded lightweight eligibility checks
no config reconciliation mutation
no Gateway action
no inference retry
no delivery retry
```

Periodic scheduler invocation may still occur if required by the platform, but the invocation must short-circuit through a low-cost read-only path before expensive or side-effecting work begins.

### 3.2 Single wake authority

For any exact durable work item at a point in time, there must be one authoritative recovery owner.

Worker, delivery recovery, provider recovery, Host Supervisor, and session recovery must not independently decide to act on the same condition without an ownership fence.

The conceptual rule is:

```text
Actionable durable condition
  -> classify exact authority
  -> one owner acquires/claims
  -> bounded action
  -> durable outcome/release
  -> back to idle
```

### 3.3 Actionability must precede heavy work

A heavy path may run only after a cheap classifier proves that at least one condition is actionable under the same durable contract that the eventual worker uses.

A broad state such as:

- any nonterminal Ticket;
- any pending delivery row;
- any pending recovery row;
- local provider process not running;

is not sufficient by itself.

The classifier must respect relevant fences including:

- due time;
- owner session identity;
- owner generation;
- session lifecycle state;
- terminal Ticket state;
- delivery state;
- lease/claim ownership;
- provider relevance to the affected inference attempt;
- retry/attempt budget;
- stale/non-actionable age rules.

### 3.4 Provider checks are work-scoped

A local provider such as Ollama may be probed or recovered only when:

1. the local adapter is enabled/available;
2. exact current work or an explicit operator command requires that adapter; and
3. durable evidence associates the affected inference attempt with Ollama where recovery is automatic.

If OpenClaw is currently using a Cloud provider and no Ollama attempt is actionable, an Ollama process being stopped must not wake the heavy Supervisor or create recurring recovery activity.

### 3.5 Provider switching is wake-neutral

Changing provider/model through OpenClaw must not itself authorize:

- heavy Supervisor execution;
- Gateway restart;
- config reconciliation;
- local provider restart;
- Ticket recovery;
- delivery retry;
- session-generation transition.

## 4. Wake classifier contract

v0.9.5 should expose one canonical lightweight decision result for Supervisor entry, conceptually:

```text
WakeDecision {
  actionable: boolean
  authority: none | ticket | direct_recovery | delivery | provider_local | session
  workId: optional exact durable identity
  reason: stable classification
}
```

The exact implementation language/type may differ, but every heavy Supervisor transition must be explainable by one durable wake decision.

If `actionable=false`, the heavy legacy reconciliation path must not run.

## 5. Stale-state behavior

Stale state must not become a permanent wake source.

For stale pending delivery/recovery rows:

- if no longer actionable, return idle;
- if terminally obsolete, reconcile or quarantine them through one bounded cleanup owner;
- do not retry indefinitely from a periodic poller;
- do not let historical attempt count alone keep the system awake;
- do not regenerate inference when a durable final payload already exists.

## 6. Polling and scheduler rules

Polling frequency is secondary to wake correctness, but v0.9.5 must also avoid redundant polling architecture.

Rules:

- prefer one scheduler entry point for periodic Host/Supervisor reconciliation;
- prefer event-driven wake when OpenClaw hooks provide exact evidence;
- do not add another recurring scheduler to solve a condition already visible to the canonical Supervisor;
- local adapter health checks must not run on their own recurring loop unless explicitly justified and isolated from healthy idle behavior;
- any periodic task must have a cheap no-work path and bounded execution time.

## 7. User-visible responsiveness acceptance

The release must include a live Windows idle-quiescence acceptance check.

With CogentNexus enabled, Gateway healthy, no actionable Ticket/recovery/delivery work, and no explicit local-provider command:

- the desktop must remain responsive;
- recurring CogentNexus activity must not produce visible periodic busy-cursor/spinner behavior attributable to CNX;
- no repeating heavy Supervisor process chain should appear;
- no repeating provider process start/probe/restart chain should appear;
- no config rewrite loop should occur.

This is a release gate, not an optional performance observation.

## 8. Instrumentation requirements

The implementation should make wake reasons observable without making healthy idle noisy.

At minimum, diagnostic output/tests should be able to distinguish:

```text
idle/no-actionable-work
wake/ticket
wake/direct-recovery
wake/delivery
wake/local-provider
wake/session
```

Repeated identical idle diagnostics should not flood logs.

For live acceptance, evidence should include enough data to prove that scheduled Supervisor invocations took the fast path and did not launch heavy recovery.

## 9. Required TDD cases

At minimum, tests must cover:

1. no Tickets/recovery/delivery -> Supervisor fast-idle, heavy path not invoked;
2. accepted Direct Ticket without due recovery -> idle;
3. pending delivery that is stale/non-actionable -> idle;
4. pending delivery with obsolete session generation -> idle/fail-closed;
5. owner session in deleting/deleted/non-authoritative state -> idle for inference recovery;
6. exact due recovery with active owner/generation -> one wake authority;
7. duplicate scheduler tick while claim/lease held -> second tick does not perform duplicate work;
8. Cloud inference active + Ollama stopped + no Ollama work -> no Ollama probe/restart wake;
9. exact Ollama attempt with explicit provider-failure evidence -> local-provider recovery may wake once under claim;
10. provider/model switch only -> zero wake/config/Gateway/local-provider actions;
11. durable final payload awaiting delivery -> delivery recovery may wake, inference recovery must not;
12. terminal Ticket plus stale auxiliary rows -> no repeated heavy wake after bounded reconciliation.

## 10. Performance/idle release gate

For the exact v0.9.5 candidate, release acceptance must prove:

```text
Healthy idle:
  scheduled tick -> lightweight classification -> idle

No actionable work:
  heavy supervisor calls = 0
  provider recovery actions = 0
  config mutations = 0
  gateway lifecycle actions = 0
```

A bounded administrative operation such as enable/disable/install/reset is excluded from idle measurement because it is intentionally active work.

## 11. Relationship to existing safety fixes

Existing actionability improvements in `durable_work_hint()` and deleting-session/stale-delivery regressions are KEEP behavior. v0.9.5 should consolidate them into the canonical single-wake architecture rather than regress or duplicate them.

The goal is not merely to reduce a timer interval or remove the Scheduled Task. A periodic tick is acceptable if its healthy path is truly cheap, side-effect-free, and incapable of waking heavy work without exact durable authority.

## 12. Final decision

v0.9.5 release semantics include operational quietness:

> No actionable work -> no heavy wake -> no provider action -> no config action -> no Gateway action.

When actionable work exists:

> Exact durable authority -> exactly one bounded owner -> bounded action -> durable convergence -> return to idle.

Any implementation that preserves functional correctness but causes recurring unnecessary background work or user-visible busy/spinner behavior fails the v0.9.5 release contract.
