# CogentNexus-OpenClaw v0.9.5 Local Provider Command Contract

Date: 2026-09-09
Status: Approved normative amendment
Target release: v0.9.5
Working branch: `agent/v0.9.5-architecture-repair`
Parent design: `docs/superpowers/specs/2026-09-09-v0.9.5-architecture-repair-design.md`

## 1. Purpose

This document is a normative amendment to the approved v0.9.5 architecture-repair design.

It resolves the command-surface question for provider handling and removes an important source of architectural coupling: provider selection MUST NOT be encoded in normal `cnxclaw` lifecycle commands.

Where this document conflicts with the parent design's older provider-command wording or deferred questions, this document takes precedence.

## 2. Core command invariant

> Provider/model routing belongs to OpenClaw. Local process management may belong to an optional CogentNexus local adapter. CogentNexus capability belongs to neither provider routing nor local process state.

Therefore:

- `cnxclaw` MUST NOT select the active inference provider;
- `cnxclaw` MUST NOT select the active model;
- switching provider/model through OpenClaw MUST NOT require a CogentNexus lifecycle command;
- CogentNexus MUST remain active and fully capable while OpenClaw changes provider/model;
- local-process lifecycle commands MUST be clearly separated from CogentNexus/OpenClaw lifecycle commands.

## 3. CogentNexus lifecycle commands

The primary lifecycle surface is provider-neutral:

```text
cnxclaw status
cnxclaw start
cnxclaw stop
cnxclaw restart
cnxclaw enable
cnxclaw disable
cnxclaw reset
cnxclaw uninstall
```

These commands MUST NOT imply provider selection.

In particular:

```text
cnxclaw start
```

means start/resume the CogentNexus-managed runtime boundary needed for CogentNexus operation. It does not mean "select and start Ollama as the inference provider".

Likewise:

```text
cnxclaw stop
```

must not silently reinterpret the user's currently selected OpenClaw provider route.

## 4. Gateway commands

Gateway lifecycle remains separately addressable:

```text
cnxclaw gateway start
cnxclaw gateway stop
cnxclaw gateway restart
```

These commands control the OpenClaw Gateway boundary only and MUST NOT select a provider/model.

## 5. Local adapter namespace

Optional locally controllable inference services use an explicit `local` namespace.

For Ollama:

```text
cnxclaw local ollama status
cnxclaw local ollama check
cnxclaw local ollama start
cnxclaw local ollama stop
cnxclaw local ollama restart
```

The word `local` is deliberate. CogentNexus has lifecycle authority here because the target is a local process/service it can actually observe and control, not merely because the target is an inference provider.

## 6. Local Ollama semantics

The Ollama adapter may provide:

- process/service health inspection;
- readiness checks;
- explicit operator-requested start/stop/restart;
- narrowly authorized recovery for an inference attempt proven to be using Ollama.

The Ollama adapter MUST NOT:

- select Ollama as OpenClaw's current inference route;
- modify OpenClaw provider/model routing as a side effect of local lifecycle management;
- enable or disable CogentNexus Ticket/Durable capability;
- force a Host-mode transition merely because Ollama starts or stops;
- wake Ollama in the background when no relevant Ollama inference attempt requires it.

Example:

```text
cnxclaw local ollama start
```

means only "ensure the local Ollama service is started according to the supported local adapter contract".

Afterward, OpenClaw may still be configured to use OpenAI, Anthropic, Gemini, or another route. The local Ollama command does not change that route.

## 7. Cloud providers

CogentNexus does not expose lifecycle namespaces such as:

```text
cnxclaw local openai ...
cnxclaw local anthropic ...
cnxclaw local gemini ...
```

for ordinary Cloud services because CogentNexus does not own those remote service lifecycles.

Provider/model selection for those services remains native OpenClaw behavior.

## 8. `cnxclaw cloud`

`cnxclaw cloud` is no longer a required or preferred v0.9.5 operation.

The command MUST NOT be used to enter a reduced-capability CogentNexus mode.

The implementation SHOULD retain it for one compatibility release only if removing it would create avoidable upgrade breakage. If retained in v0.9.5, it MUST:

- be explicitly deprecated;
- perform no provider/model/auth selection;
- perform no reduced-capability `providerMode=passthrough` transition;
- avoid Gateway restart unless another explicit administrative invariant independently requires one;
- direct the operator to use normal OpenClaw provider selection instead.

The preferred future state is removal after the compatibility window.

## 9. Legacy `--provider` compatibility

Legacy commands such as:

```text
cnxclaw start --provider ollama
cnxclaw stop --provider ollama
```

MUST NOT remain part of the primary v0.9.5 command contract.

For v0.9.5, the preferred migration behavior is deprecation rather than abrupt breakage.

A legacy invocation MAY be accepted for one compatibility release, but it MUST NOT select or rewrite the OpenClaw inference route.

The compatibility layer should emit a clear deprecation diagnostic directing the user to:

```text
cnxclaw start
```

for CogentNexus lifecycle, and:

```text
cnxclaw local ollama start
```

for local Ollama lifecycle.

The implementation plan must make compatibility behavior deterministic and covered by tests.

## 10. Legacy provider checks

Legacy:

```text
cnxclaw check provider ollama
```

may remain as a one-release compatibility alias for:

```text
cnxclaw local ollama check
```

provided that the alias:

- does not read or alter OpenClaw provider selection;
- does not imply CogentNexus supports only Ollama;
- emits deprecation guidance where appropriate;
- is covered by exact compatibility tests.

## 11. Target command tree

The preferred v0.9.5 operator surface is:

```text
cnxclaw
├── status
├── start
├── stop
├── restart
├── enable
├── disable
├── reset
├── uninstall
│
├── gateway
│   ├── start
│   ├── stop
│   └── restart
│
├── local
│   └── ollama
│       ├── status
│       ├── check
│       ├── start
│       ├── stop
│       └── restart
│
├── ticket
├── session
└── policy
```

Provider/model selection intentionally does not appear in this tree.

## 12. Supervisor implications

The Supervisor must treat local adapters as conditional capabilities rather than global desired-provider state.

Therefore:

- no global `desiredProvider=running` authority should cause Ollama recovery while OpenClaw is using another provider;
- local recovery authority must be tied to exact attempt/provider evidence;
- stopping Ollama must not disable CogentNexus;
- changing OpenClaw provider must not alter local adapter configuration automatically;
- normal provider switching must generate zero CNX config writes.

## 13. Migration requirements

During v0.9.4 -> v0.9.5 upgrade:

- existing OpenClaw provider/model/auth route must be preserved exactly;
- legacy provider-oriented CNX settings must not overwrite the OpenClaw route;
- v0.9.4 Cloud pass-through + plugin-enabled state must migrate to active v0.9.5 capability;
- legacy Ollama lifecycle state may be translated into local-adapter state only where that translation is deterministic and does not imply provider selection.

## 14. Required TDD cases

Before production command changes, tests must prove the old coupling and the new contract.

At minimum:

1. `cnxclaw start` does not select or rewrite provider/model route.
2. `cnxclaw stop` does not rewrite provider/model route.
3. `cnxclaw local ollama start` starts/probes only Ollama and leaves OpenClaw route unchanged.
4. `cnxclaw local ollama stop` stops only Ollama and leaves CNX capability active unless an explicit broader lifecycle command says otherwise.
5. changing OpenClaw provider while CNX is active requires no `cnxclaw` provider command.
6. legacy `start --provider ollama` cannot select the OpenClaw route.
7. legacy `check provider ollama`, if retained, is behaviorally equivalent to `local ollama check` and side-effect-free with respect to route selection.
8. `cnxclaw cloud`, if retained, cannot reduce Ticket/Durable capability or change provider/model/auth.
9. unknown/future OpenClaw providers require no new `cnxclaw provider` command.
10. local Ollama failure while the active attempt uses a Cloud provider does not trigger unsolicited Ollama restart.

## 15. Documentation requirements

Current operator documentation for v0.9.5 must describe three separate concepts explicitly:

```text
Provider/model routing      -> OpenClaw
CogentNexus lifecycle       -> cnxclaw top-level lifecycle commands
Local Ollama management     -> cnxclaw local ollama ...
```

Documentation must not describe Ollama as the only CogentNexus inference provider. It may describe Ollama as the currently supported CogentNexus-managed local process adapter.

## 16. Final decision

v0.9.5 removes provider selection from CogentNexus lifecycle semantics.

The stable contract is:

> Provider routing = OpenClaw.
> Local process management = optional CogentNexus local adapter.
> CogentNexus capability = provider-independent.

This command separation is release-critical and must be included in the implementation plan, behavior matrix, migration tests, and final acceptance criteria.
