# v0.9.5 Plan 2 Session Generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Centralize the physical-session generation rule so only a real ownership boundary can advance generation, while provider/model/runtime changes remain generation-neutral.

**Architecture:** `cnx_sessions` remains the single durable lifecycle authority. The new helper only decides whether an event represents a physical ownership boundary; it does not store sessions or create a second lifecycle source of truth. Existing deletion/recreation semantics remain authoritative in `v090.ts` and continue to use the tombstoned generation for the genuinely new lifecycle.

**Tech Stack:** TypeScript, Node `node:sqlite`, Vitest, existing CogentNexus-OpenClaw session ownership implementation.

**Spec:** `docs/superpowers/specs/2026-09-09-v0.9.5-architecture-repair-design.md` and `docs/superpowers/plans/2026-09-09-v0.9.5-delivery-session-identity-repair.md`

## Global Constraints

- `sessionKey + sessionId + generation` is lifecycle identity; `sessionKey` alone is not sufficient.
- Delete/replace/rotate are physical ownership boundaries.
- Provider change, model change, compaction, and Gateway restart do not advance generation when the physical session remains the same.
- No new session store may be introduced.
- Existing `v090.ts` remains the durable owner of `cnx_sessions`.
- Old lifecycle work must remain fenced after generation rotation.
- No release/tag/public-version mutation is part of this plan.

## Identity-gap resolution

The earlier review identified that canonical attempt/delivery records persist `sessionKey + generation` rather than carrying `sessionId` directly. The Plan 2 gate was resolved without changing that persistence shape because the durable lifecycle invariant is stronger at the ownership boundary:

1. Physical lifecycle S1 begins at generation 0 and owns its authoritative `cnx_sessions.session_id`.
2. Physical deletion advances the durable generation to 1 before tombstoning the session.
3. Genuine recreation as S2 on the same `sessionKey` reuses the tombstoned generation 1 rather than incrementing again.
4. Stale work created under S1 retains generation 0.
5. Attempt bind/finish and Delivery Core owner checks compare the recorded generation against the currently active `cnx_sessions` generation and fail closed for stale work.
6. The new regression test proves the S1 attempt cannot bind or finish after S2 recreation and does not create a new Run lookup for stale evidence.

Therefore, although `sessionId` is not duplicated into every attempt/delivery row, the current authoritative `cnx_sessions` generation transition makes prior-session work observably stale and prevents cross-incarnation acceptance at the lifecycle boundary tested by Plan 2.
